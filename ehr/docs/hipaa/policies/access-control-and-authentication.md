## 1. Purpose
Only authorized people may access ePHI, and each person gets only the access their job needs.

## 2. Scope
This policy covers:
- the Clinic Ready EHR;
- the hosting account (Render);
- the source repository (GitHub);
- CollaborateMD, email, fax, telehealth, and phone/SMS systems;
- the password manager;
- all workforce members, including contractors, students, and volunteers.

## 3. Policy

### 3.1 Unique accounts
- 3.1.1 Every person has their own account in each system. **Shared or generic logins are prohibited.** That includes "frontdesk@" logins and sharing a clinician's session.
- 3.1.2 Accounts are requested by `[supervisor]` and approved by the Security Officer, using the role matrix. The admin creates the account in **EHR → Admin → Users** only after the person has completed training and signed the attestation.
- 3.1.3 Use the least-privileged role that covers the job. The **admin** role goes only to `[Owner, Security Officer]`. Admins use a non-admin account for daily clinical work where practical `[decide]`.

### 3.2 Passwords
- 3.2.1 The EHR requires at least 12 characters with 3 of 4 character classes. Workforce members should use a passphrase of 15 or more characters generated by or stored in the practice password manager `[name]`.
- 3.2.2 Passwords are never shared, written on paper at the workstation, or reused from personal accounts.
- 3.2.3 Change a password right away if compromise is suspected. Routine forced expiry isn't required; current NIST SP 800-63B guidance advises against arbitrary periodic changes.
- 3.2.4 After 5 failed attempts the EHR locks the account for 15 minutes. Repeated lockouts are investigated (see the audit policy).

### 3.3 Multi-factor authentication
- 3.3.1 Everyone with EHR access must enroll in TOTP two-factor sign-in (implemented in this release; verify after deployment). After enrollment is complete, `EHR_REQUIRE_MFA=1` stays set in production.
- 3.3.2 MFA is also required on Render, GitHub, CollaborateMD `[if supported]`, email, and the password manager.
- 3.3.3 Recovery codes are stored in the password manager, never in email or on paper at the workstation.
- 3.3.4 Losing an MFA device: report it to the Security Officer the same day. The admin resets MFA after verifying the person's identity in person or by a known phone number.

### 3.4 Sessions and automatic logoff
- 3.4.1 The EHR signs users out after **30 minutes idle** and after **12 hours** regardless of activity. `EHR_IDLE_MINUTES` must not be raised above 30 without a documented risk decision.
- 3.4.2 Lock the screen (Win+L or Ctrl+Cmd+Q) whenever you step away. Devices auto-lock after `[5]` minutes; see [device-and-media.md](device-and-media.md).
- 3.4.3 Sign out of the EHR at the end of each day, and always on shared devices.

### 3.5 Access changes and reviews
- 3.5.1 Role changes are requested in writing (email to the Security Officer), and the admin makes them. Every change is audited by the EHR.
- 3.5.2 **Termination:** access is removed **by the end of the last day of work, or immediately for an involuntary termination**. Deactivating the user in the EHR revokes all of their sessions. Remove them from every other system on the offboarding checklist (see the workforce policy).
- 3.5.3 **Quarterly access review:** the Security Officer compares the EHR user list (Admin → Users) and every vendor account list against the current staff roster and roles, then records the result:

| Date | Systems reviewed | Accounts removed or changed | Reviewer |
|---|---|---|---|
| | | | |

### 3.6 Emergency access ("break glass")
- 3.6.1 The EHR doesn't restrict charts by care team, so clinicians can open any chart in an emergency without special steps. The audit log records that access.
- 3.6.2 If no admin can sign in (for example, lost credentials or MFA), the Security Officer or Owner uses the documented recovery:
  1. In the hosting dashboard, set `EHR_ADMIN_EMAIL`, a new strong `EHR_ADMIN_PASSWORD`, and `EHR_ADMIN_RESET=1`.
  2. Restart the service. The admin is reset, unlocked, and reactivated, and the reset is audited as `admin_reset`.
  3. Sign in.
  4. **Immediately remove `EHR_ADMIN_RESET` and `EHR_ADMIN_PASSWORD`** and restart.
  5. Record the event in the incident log with the reason.
- 3.6.3 Hosting-account recovery details (who holds Render owner access) are stored in `[sealed escrow location]`.

### 3.7 Hosting and code access
- 3.7.1 Render workspace members are limited to `[names]`. Only these people can see environment variables (including keys) or open a shell.
- 3.7.2 Changes to the production branch require `[review by a second person / Security Officer approval]`. `[Decide whether to turn off autoDeploy.]`
- 3.7.3 Real PHI is never put in the source repository, issue trackers, chat tools, AI tools, or test data, unless that vendor is under a BAA and the use is approved.

## 4. Responsibilities
- **Security Officer:** approves access, runs the quarterly review, handles recovery.
- **Supervisors:** request access changes promptly.
- **Workforce:** protects their credentials and reports suspected compromise immediately.

## 5. Enforcement
Violations are handled under the sanctions policy.
